# Activities, Tasks & Timeline

**Status:** Planned · **Phase:** 3 · **Depends on:** platform, records

---

## 1. Purpose

What happened, and what should happen next. The timeline is the narrative of a
relationship; tasks are the commitments against it.

---

## 2. The separation that makes this work

The brief says *"Every action creates an activity. … Stage Change. Assignment.
Everything."* That merges two systems with opposite requirements:

| | **Activity** (timeline) | **Audit Event** |
|---|---|---|
| Audience | Salespeople | Compliance, security, support |
| Volume | Low, curated | Very high, every mutation |
| Editable | Yes — fix a mistyped call note | **Never** |
| Deletable | Yes | **Never** |
| Retention | User's choice | Fixed by policy |
| Schema | Typed, configurable per workspace | Uniform, generic |

Merged, you get a timeline nobody reads — drowned in
`custom_field_47: null → ""` — and an audit log that fails its first review
because users can delete from it.

**Two stores** (FR-ACT-001). Selected audit events *project* into the timeline —
stage changes, owner changes, verdict changes — and **which ones is
configurable** (FR-ACT-004). That is how the brief's intent is honoured without
its consequence.

---

## 3. Configuration surface

Activity types (key, label, icon, colour, own fields, manually loggable) ·
which audit events project into the timeline · task priorities and statuses ·
reminder defaults · notification channels per user · working days and holidays.

`email`, `call`, `meeting` are **seed data**, not enum members in code. A
workspace adding "Kickoff" writes no code.

---

## 4. Behaviour

### Activities

- Attach polymorphically to account, contact, deal, proposal or agreement
- **Roll up**: an activity on a deal appears on that deal's account timeline.
  This is the most frequent read in the product and is why `account_id` is
  denormalised onto attachments ([05](../05_DATABASE_DESIGN.md#polymorphic-attachment)).
- Carry `occurred_at` distinct from `created_at` — logging Tuesday's call on
  Thursday must place it on Tuesday
- Editable and deletable by permitted users; every edit is audited

### Tasks

- Attach polymorphically; assignee, due date **and time**, priority, status, reminder
- Due dates stored UTC, rendered in the user's timezone (FR-ACT-007)
- Scheduling respects the workspace weekend — **default Fri–Sat** — and holidays
  (FR-ACT-008). "Due in 3 working days" is wrong for the Gulf if it assumes
  Sat–Sun.
- Overdue is computed in the *assignee's* timezone, not the server's

### Notifications

A first-class object with per-user channel preferences (FR-ACT-011), not a side
effect of other modules. Generated by assignment, mention, reminder, automation
and system events. Notification without preferences is how products get muted.

---

## 5. Interfaces

**Offers:** log activity, CRUD tasks, timeline query with filters, mark complete,
bulk reassign, notification preferences.

**Emits:** `activity.logged`, `task.created/completed/overdue`, `note.mentioned`.

**Consumes:** every module's events, for timeline projection where configured.

---

## 6. UI surfaces

Timeline (chronological, icons, rich previews, filter by type/user/date) ·
activity composer · task list (my tasks, team tasks, overdue) · task quick-create
from any record · calendar view · notification centre · @mention autocomplete.

The timeline is a signature surface. It must stay readable at 500 entries —
which means grouping by day, collapsing runs of similar events, and never showing
raw field diffs unless asked.

---

## 7. Edge cases

| Case | Behaviour |
|---|---|
| Activity on a deleted record | Retained, marked orphaned, visible in audit |
| Task assigned to a deactivated user | Surfaced for reassignment, never silently dropped |
| Backdated activity | Placed by `occurred_at`; `created_at` visible on hover |
| Timezone change by a user | Existing due dates unchanged in absolute time; display shifts |
| Task due on a weekend | Allowed manually; automation-generated dates skip to the next working day |
| Bulk reassign of 5,000 tasks | Background job with progress and partial-failure report |
| Mention of a user without record access | Mention blocked with explanation — mentions must not leak record contents |
| Very long timeline | Paginated with day grouping; similar consecutive events collapse |
| Automation generating hundreds of activities | Rate-limited per record; loop protection applies |

## 8. Acceptance criteria

- [ ] Activities and audit events are separate stores with separate retention (FR-ACT-001)
- [ ] Audit events cannot be edited or deleted by any user (FR-ACT-003)
- [ ] Which audit events project into the timeline is configurable (FR-ACT-004)
- [ ] A new activity type is created by an admin with no code change (FR-ACT-002)
- [ ] Deal activities appear on the account timeline (FR-ACT-005)
- [ ] Due dates are correct across timezones (FR-ACT-007)
- [ ] Automation-generated dates respect a Fri–Sat weekend (FR-ACT-008)
- [ ] Timeline remains responsive at 500+ entries
- [ ] Mentions notify only users who can see the record
