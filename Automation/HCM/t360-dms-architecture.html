Architecture Review — Pre-Build

The Document Management System, designed around Opportunities

Your brief already has the right instinct — Opportunity as source of truth, document data kept separate, one reusable engine, an application-grade UX instead of raw sheet editing. Below: where I'm keeping that instinct exactly, where I'm changing the mechanics underneath it, and why — followed by the full data model, navigation, module breakdown, and engine design.

01Verdict on your design

Four places where the brief implies a mechanism but doesn't specify one. I picked the mechanism in each case — three are structural changes, two are pure endorsements.

Kept

Opportunity as source of truth, wizard-driven generation, one shared engine. Correct on all three. This is exactly the Salesforce CPQ / HubSpot Quotes shape: a durable parent record, ephemeral per-document forms, one pipeline that stamps out any document type.

Changed

Document-specific data storage. The brief says "don't build one giant sheet" but doesn't say what replaces it. The tempting shortcut is a single wide sheet with every field from every template, mostly blank per row — exactly the anti-pattern you're rejecting, just deferred. I'm using four dedicated sheets, one per template, each with only that template's own columns. Native to Sheets, filterable by your team without touching code, and each one evolves independently — add a column to the Agreement sheet without touching the Proposal sheet.

Changed

"Services should remain synchronized" between HCM Proposal and Agreement. Read literally, this asks for a sync mechanism — write in two places, keep them equal. That's a bug waiting to happen (they will eventually drift). The actual fix is to not store it twice: one shared HCM Service Selection table per Opportunity, and both HCM documents read from it. Synchronization by construction, not by discipline.

Changed

Document-specific data vs. Document History as two separate concerns. Treated as genuinely separate stores, you'd either duplicate every field per version (bloat) or store history without the field values (can't inspect or clone an old version). Instead: every row in a template's data sheet is already a version — regenerating appends a new row, nothing is overwritten. A slim cross-cutting Documents sheet indexes all four, giving you the Opportunity-level "everything generated for this deal" rollup without duplicating field data.

02Template findings

All four templates analyzed at the XML level, the same way the HCM Proposal template was built. Two hard requirements confirmed, two issues to flag before I wire anything to these files.

Data hygiene — Offshoring Agreement

This file isn't a blank master. The Party 1 signature block still contains a real former client's name, تيك استرايك ("Tech Strike"), typed in as static highlighted text rather than a placeholder. I've treated it as {{CLIENT_NAME}} since that's clearly its intent, but I only inspected the highlighted runs — the surrounding prose wasn't fully re-read for other leftover deal-specific numbers. Worth a skim before this becomes the live master template.

Likely drafting gap — HCM Agreement

Article 1 statically lists all seven HCM services as numbered sub-clauses. The pricing table's service-scope cell, which should mirror that same list, is missing Performance Management — six services instead of seven. Once this list is engine-generated from the shared service selection instead of hand-typed, this class of bug becomes structurally impossible. Recommend restoring the seventh service now rather than preserving the gap.

05Apps Script architecture

Ten server-side modules, four HTML dialogs. Each module has exactly one reason to change.

ModuleResponsibility
Config.gsSheet names, per-sheet column headers, status enums, ID prefixes. The only file with literal strings in it.
Helpers.gsHeader-name column lookup, row↔object conversion, ID generation, date normalization, regex-safe escaping — same primitives proven in the HCM Proposal build.
SettingsService.gsReads the Settings sheet into one cached config object; writes from the Settings dialog.
OpportunityService.gsCRUD for Opportunities; Opportunity ID generation; reads/writes HCM Service Selection.
DocumentTypeRegistry.gsThe 4 document types as data: which sheet, which template setting, which fields belong in the wizard form, which dynamic blocks (if any) it has. Adding a 5th document type later is one entry here.
DocumentEngine.gsThe one reusable pipeline: duplicate template → apply dynamic blocks → replace placeholders → save → return URL. Generalized from the proven {{SEC:}}/{{NUM:}} mechanism to work for any numbering format.
ValidationService.gsSchema-driven required-field checks (from the Registry) + environment checks (template/sheet exist), same friendly-dialog pattern as before.
HistoryService.gsAppends a version row to the right data sheet, indexes it into Documents, fetches an Opportunity's full history, fetches a prior version for regeneration pre-fill.
UI.gsThe controller between HTML and services — every google.script.run call the dialogs make lands here.
Menu.gsonOpen() only. Four menu items, four dialog launches.

Plus OpportunityDialog.html, GenerateWizard.html, HistorySidebar.html, SettingsDialog.html — each a thin view over the same UI.gs controller functions.

06Document engine

One engine, driven entirely by data from DocumentTypeRegistry.gs — it has no HCM-specific or Arabic-specific code in it.

Every document type is described the same shape:

The block-renumbering step is the same generalized routine for both agreements and proposals: locate each enabled block by its control token, delete disabled ones, then walk the survivors in one fixed order and hand each the next number in that type's format function — n => "3." + n for the Proposal, n => n + "." for the Arabic Agreement. Everything else — duplicate, replace, save, return URL — is identical code across all four document types.
